Предлагаю зафиксировать **HTTP API `/api/v1` и один WebSocket `/api/v1/ws`**. Через HTTP — авторизация, загрузка мира и фотографии. Через WebSocket — движение, чат и общение с гидами.

Ниже — первоначальный контракт, по которому фронтендер и бэкендер уже могут работать параллельно. Это проект вашего API, поэтому имена полей и поведение можно принять сразу как версию `v1`.

**1. Общие соглашения**

| Правило | Значение |
|---|---|
| HTTP base path | `/api/v1` |
| Формат данных | JSON, поля в `snake_case` |
| Идентификаторы | Непрозрачные строки: клиент не разбирает их структуру |
| Время | UTC, RFC 3339: `2026-10-31T12:00:00Z` |
| Расстояния | Метры |
| Координаты | Правая система, `Y` вверх |
| Начальное направление взгляда | Вдоль `-Z` |
| Углы | Радианы |
| `yaw` | Поворот вокруг `+Y`, по правилу правой руки |
| `pitch` | Положительный угол — взгляд вверх |
| Авторизация | Cookie `museum_session` |
| Версия мира | Неизменна в пределах запуска демонстрационной сборки |

Положение игрока — точка на полу под ним. Высоту камеры клиент добавляет сам. Для первой версии принимаем высоту камеры **1,65 м**, радиус игрока **0,3 м**.

Пример:

```json
{
  "position": {"x": 2.5, "y": 0, "z": -4.0},
  "rotation": {"yaw": 1.2, "pitch": 0.1}
}
```

Успешные HTTP-ответы возвращают объект непосредственно, без общей обёртки `data`. Ошибки имеют единый формат:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные",
    "fields": {
      "username": "Длина должна быть от 3 до 32 символов"
    },
    "request_id": "req_01"
  }
}
```

`fields` присутствует только при ошибках отдельных полей. Клиент принимает решения по `code`, а `message` использует для отображения.

| HTTP | Примеры кодов |
|---|---|
| `400` | `INVALID_JSON`, `VALIDATION_ERROR` |
| `401` | `UNAUTHENTICATED`, `INVALID_CREDENTIALS` |
| `403` | `FORBIDDEN`, `ROOM_NOT_ACCESSIBLE` |
| `404` | `NOT_FOUND` |
| `409` | `USERNAME_TAKEN`, `WORLD_VERSION_MISMATCH` |
| `413` | `PAYLOAD_TOO_LARGE` |
| `429` | `RATE_LIMITED`, `GUIDE_QUEUE_FULL` |
| `503` | `AI_UNAVAILABLE` |

**2. HTTP: авторизация и состояние игрока**

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/auth/register` | Создать аккаунт и сессию |
| `POST` | `/auth/login` | Создать сессию |
| `POST` | `/auth/logout` | Завершить текущую сессию |
| `GET` | `/me` | Получить пользователя и сохранённое состояние |

`POST /auth/register`

```json
{
  "username": "cunev",
  "display_name": "Валентин",
  "password": "museum-password"
}
```

Ограничения:

- `username`: 3–32 ASCII-символа, латиница, цифры, `_`; регистр не учитывается;
- `display_name`: 1–32 символа после удаления пробелов по краям;
- `password`: 8–128 байт UTF-8.

Ответ `201 Created`, устанавливается cookie:

```json
{
  "user": {
    "id": "usr_01",
    "username": "cunev",
    "display_name": "Валентин",
    "avatar_color": "#5B8DEF"
  }
}
```

`POST /auth/login`

```json
{
  "username": "cunev",
  "password": "museum-password"
}
```

Ответ `200 OK` того же формата, что при регистрации.

`POST /auth/logout` → `204 No Content`. Сервер отзывает сессию, удаляет cookie и закрывает связанные с этой сессией WS-соединения.

`GET /me` → `200 OK`:

```json
{
  "user": {
    "id": "usr_01",
    "username": "cunev",
    "display_name": "Валентин",
    "avatar_color": "#5B8DEF"
  },
  "player_state": {
    "room_id": "room_egypt_01",
    "position": {"x": 2.5, "y": 0, "z": -4.0},
    "rotation": {"yaw": 1.2, "pitch": 0.1}
  }
}
```

**Правила сессии:** срок — 24 часа без продления для первой версии; cookie `HttpOnly`, `SameSite=Lax`, `Path=/`. `Secure` включается при HTTPS. Для изменяющих запросов проверяется `Origin`; для WebSocket — тоже. Сессия проверяется до WS upgrade, после истечения соединение закрывается.

Сохранённая позиция из `/me` нужна для первоначального UI. **При входе в игровой мир окончательное положение задаёт WS-событие `world.snapshot`.**

**3. HTTP: мир и его загрузка**

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/world/manifest` | Версия мира и бюджет клиентского кеша |
| `GET` | `/world/rooms/{room_id}?version={version}` | Описание доступного зала |
| `GET` | `/world/assets/{asset_id}?version={version}` | Изображение или модель |

Все три маршрута требуют сессию. Доступ к залу и его ресурсам сервер проверяет по текущему положению игрока.

`GET /world/manifest`

```json
{
  "world_id": "museum",
  "world_version": "world_v1",
  "total_content_bytes": 100000000,
  "client_cache_limit_bytes": 10000000,
  "max_loaded_rooms": 2,
  "movement": {
    "send_rate_hz": 10,
    "max_speed_mps": 4.0,
    "player_radius_m": 0.3,
    "camera_height_m": 1.65
  }
}
```

Манифест не содержит полного списка экспонатов и геометрии мира.

**Единица учёта кеша:** размер уникальных файлов контента до HTTP-сжатия, включая описания залов, изображения и модели. Сервер вычисляет общий объём при подготовке мира. Это проектная трактовка требования 10%; её нужно согласовать с организаторами.

Клиент учитывает загруженные файлы и резервирует место под незавершённые загрузки. Повторно используемый файл считается один раз. Декодированная RAM/GPU-память измеряется отдельно.

Список доступных залов приходит через WebSocket:

```json
{
  "room_id": "room_egypt_01",
  "descriptor_bytes": 2400,
  "assets": [
    {
      "id": "asset_egypt_01",
      "bytes": 180000,
      "content_type": "image/webp"
    }
  ]
}
```

Благодаря этому клиент проверяет бюджет **до загрузки описания и изображений**.

`GET /world/rooms/room_egypt_01?version=world_v1`

```json
{
  "id": "room_egypt_01",
  "world_version": "world_v1",
  "title": "Древний Египет",
  "bounds": {
    "min": {"x": 0, "y": 0, "z": -12},
    "max": {"x": 12, "y": 4, "z": 0}
  },
  "surfaces": [
    {
      "id": "wall_01",
      "position": {"x": 6, "y": 2, "z": -12},
      "size": {"x": 12, "y": 4, "z": 0.2},
      "color": "#E8DFCF",
      "collidable": true
    }
  ],
  "exhibits": [
    {
      "id": "exhibit_01",
      "title": "Искусство Древнего Египта",
      "description": "Краткое описание экспоната.",
      "image_asset_id": "asset_egypt_01",
      "position": {"x": 6, "y": 1.8, "z": -11.8},
      "rotation_y": 0,
      "width_m": 1.5,
      "height_m": 1.0
    }
  ],
  "guides": [
    {
      "id": "guide_herodotus",
      "display_name": "Геродот",
      "subtitle": "Историк и путешественник",
      "position": {"x": 3, "y": 0, "z": -6},
      "rotation_y": 0,
      "interaction_radius_m": 3
    }
  ]
}
```

Для первой версии `surfaces` — прямоугольные блоки без вращения: стены, пол, потолок. Это позволяет одинаково реализовать простые коллизии на клиенте и сервере.

Экспонат при `rotation_y = 0` обращён лицевой стороной к `+Z`; `position` — его центр. Все координаты глобальные.

**Критические правила:**

- `surfaces` и остальные массивы описывают только один зал;
- текущий зал всегда целиком помещается в бюджет;
- доступность соседнего зала не означает обязанность его загружать;
- при нехватке бюджета клиент сначала освобождает старые данные;
- ресурсы мира возвращаются с `Cache-Control: no-store`;
- изменение списка доступных залов не заменяет проверку доступа на HTTP-маршрутах.

**4. WebSocket: формат сообщений**

Подключение:

```text
ws://<server>/api/v1/ws
```

При HTTPS используется `wss://`. Cookie браузер передаёт автоматически.

Клиентское сообщение:

```json
{
  "type": "chat.send",
  "request_id": "req_123",
  "payload": {
    "text": "Привет!"
  }
}
```

Серверное сообщение:

```json
{
  "type": "chat.message",
  "event_id": "evt_456",
  "request_id": "req_123",
  "server_time": "2026-10-31T12:00:00Z",
  "payload": {}
}
```

- `request_id` обязателен для команд, кроме `player.move`.
- В серверном сообщении `request_id` присутствует только у ответа отправителю.
- `event_id` идентифицирует событие, но не обещает его восстановление после переподключения.
- Ошибка команды возвращается событием `error` с исходным `request_id`.
- Неизвестный `type` → `UNKNOWN_EVENT`.

Первое серверное сообщение — `world.snapshot`:

```json
{
  "type": "world.snapshot",
  "event_id": "evt_001",
  "server_time": "2026-10-31T12:00:00Z",
  "payload": {
    "protocol_version": 1,
    "world_version": "world_v1",
    "self": {
      "user_id": "usr_01",
      "room_id": "room_egypt_01",
      "position": {"x": 2, "y": 0, "z": -3},
      "rotation": {"yaw": 0, "pitch": 0}
    },
    "players": [],
    "available_rooms": []
  }
}
```

`players` содержит остальных подключённых игроков с именем, цветом, комнатой, позицией и поворотом. `available_rooms` — описанные выше пакеты с размерами.

Для первой версии сервер рассылает положение всех игроков, а клиент отображает тех, чьи залы загружены. Для нескольких участников это проще, чем отдельные подписки на зоны видимости.

**5. WebSocket: движение и присутствие**

| Направление | Событие | Назначение |
|---|---|---|
| Клиент → сервер | `player.move` | Предлагаемое положение |
| Сервер → клиенты | `player.joined` | Игрок подключился |
| Сервер → клиенты | `players.state` | Подтверждённые положения |
| Сервер → клиенты | `player.left` | Игрок отключился |
| Сервер → игрок | `world.rooms_available` | Изменился набор доступных залов |

`player.move`:

```json
{
  "type": "player.move",
  "payload": {
    "seq": 42,
    "position": {"x": 2.4, "y": 0, "z": -3},
    "rotation": {"yaw": 0.3, "pitch": 0}
  }
}
```

`seq` увеличивается в пределах соединения. Клиент не передаёт собственный `user_id` и не назначает себе комнату.

Сервер проверяет скорость, коллизии и переходы, затем отправляет `players.state`:

```json
{
  "type": "players.state",
  "event_id": "evt_002",
  "server_time": "2026-10-31T12:00:01Z",
  "payload": {
    "players": [
      {
        "user_id": "usr_01",
        "ack_seq": 42,
        "room_id": "room_egypt_01",
        "position": {"x": 2.4, "y": 0, "z": -3},
        "rotation": {"yaw": 0.3, "pitch": 0}
      }
    ]
  }
}
```

Событие включает самого игрока: он использует подтверждение для коррекции локальной позиции. `ack_seq` — последний обработанный ввод; позиция может отличаться от запрошенной.

`world.rooms_available` возвращает **полную замену** списка:

```json
{
  "current_room_id": "room_egypt_02",
  "available_rooms": []
}
```

Для простоты разрешаем **одно активное игровое соединение на аккаунт**. Новое подключение заменяет старое. При переподключении клиент получает свежий snapshot, сбрасывает `seq` и не воспроизводит накопленные перемещения.

**6. WebSocket: взаимодействие игроков**

Для MVP чат общий на всю галерею.

`chat.send`:

```json
{
  "type": "chat.send",
  "request_id": "req_10",
  "payload": {
    "text": "Посмотрите на эту картину!"
  }
}
```

`chat.message`:

```json
{
  "type": "chat.message",
  "event_id": "evt_10",
  "server_time": "2026-10-31T12:01:00Z",
  "payload": {
    "message_id": "msg_01",
    "author": {
      "user_id": "usr_01",
      "display_name": "Валентин"
    },
    "text": "Посмотрите на эту картину!"
  }
}
```

Ограничение текста — 500 символов. HTML не поддерживается. Сервер проверяет частоту сообщений.

Историю общего чата в первый день можно не хранить. Диалоги с гидами сохраняются обязательно.

**7. Гиды: свободный вопрос, потоковый ответ и память**

| Направление | Событие |
|---|---|
| Клиент → сервер | `exhibit.inspect` |
| Клиент → сервер | `guide.ask` |
| Клиент → сервер | `guide.cancel` |
| Сервер → игрок | `guide.accepted` |
| Сервер → игрок | `guide.delta` |
| Сервер → игрок | `guide.completed` |
| Сервер → игрок | `guide.failed` |

Осмотр экспоната:

```json
{
  "type": "exhibit.inspect",
  "request_id": "req_20",
  "payload": {
    "exhibit_id": "exhibit_01"
  }
}
```

Сервер проверяет расстояние, сохраняет событие и отвечает `exhibit.inspected` с `exhibit_id`. Эти события становятся частью памяти гида.

Вопрос:

```json
{
  "type": "guide.ask",
  "request_id": "req_21",
  "payload": {
    "guide_id": "guide_herodotus",
    "text": "Почему на изображениях люди показаны в профиль?",
    "exhibit_id": "exhibit_01"
  }
}
```

`exhibit_id` необязателен. Максимум вопроса — 2000 символов. До постановки запроса в очередь сервер проверяет, что игрок находится рядом с гидом.

Ответы ниже показаны как `payload`; у каждого есть стандартная WS-обёртка.

`guide.accepted`:

```json
{
  "generation_id": "gen_01",
  "guide_id": "guide_herodotus",
  "user_message_id": "dialog_01",
  "queue_position": 0
}
```

`0` означает, что генерация может начаться сразу; положительное число — позиция на момент принятия.

`guide.delta`:

```json
{
  "generation_id": "gen_01",
  "index": 0,
  "text": "Ты уже рассматривал этот рельеф. "
}
```

`guide.completed`:

```json
{
  "generation_id": "gen_01",
  "message": {
    "id": "dialog_02",
    "role": "assistant",
    "text": "Полный окончательный ответ гида.",
    "created_at": "2026-10-31T12:02:00Z"
  },
  "related_exhibit_ids": ["exhibit_01"]
}
```

Полный текст в `completed` заменяет собранные фрагменты. Сервер отправляет это событие **после сохранения ответа**.

`guide.failed`:

```json
{
  "generation_id": "gen_01",
  "code": "AI_UNAVAILABLE",
  "message": "Гид временно не может ответить",
  "retryable": true
}
```

Отмена:

```json
{
  "type": "guide.cancel",
  "request_id": "req_22",
  "payload": {
    "generation_id": "gen_01"
  }
}
```

Генерация завершается событием `guide.failed` с `code: "CANCELLED"`.

**Семантика:**

- один незавершённый вопрос на пользователя;
- ответы гида получает только задавший вопрос;
- память изолирована по `user_id + guide_id`;
- личность, знания и историю формирует сервер;
- клиент не передаёт system prompt и историю сообщений;
- при разрыве WS незавершённая генерация отменяется; уже завершённые сообщения доступны через HTTP;
- автоматически повторять `guide.ask` после переподключения нельзя.

Для восстановления диалога:

```text
GET /api/v1/guides/{guide_id}/messages?limit=20&before={cursor}
```

```json
{
  "items": [
    {
      "id": "dialog_01",
      "role": "user",
      "text": "Почему на изображениях люди показаны в профиль?",
      "created_at": "2026-10-31T12:01:50Z"
    }
  ],
  "next_before": null
}
```

Внутри страницы сообщения идут от старых к новым. `before` — непрозрачный курсор; максимум `limit` — 50.

**8. Фотографии: контракт второго дня**

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/photos` | Загрузить снимок |
| `GET` | `/photos?limit=20&cursor=...` | Собственный альбом |
| `GET` | `/photos/{photo_id}/image` | Получить снимок |

`POST /photos` — `multipart/form-data`:

| Поле | Формат |
|---|---|
| `image` | JPEG или WebP |
| `caption` | Необязательная подпись, до 200 символов |
| `room_id` | Зал съёмки |
| `exhibit_id` | Необязательный экспонат |

Лимиты: **2 МиБ, максимум 1920 × 1080**, проверка реального формата на сервере. Принимать фото только при активном игровом соединении; проверять, что указанные зал и экспонат доступны игроку.

Ответ `201 Created`:

```json
{
  "id": "photo_01",
  "owner_id": "usr_01",
  "caption": "Нашли интересный экспонат",
  "room_id": "room_egypt_01",
  "exhibit_id": "exhibit_01",
  "image_url": "/api/v1/photos/photo_01/image",
  "image_bytes": 245000,
  "created_at": "2026-10-31T12:05:00Z"
}
```

Список альбома возвращает `{ "items": [...], "next_cursor": null }`. Снимок приватен до публикации.

Для отправки в общий чат расширяем `chat.send`:

```json
{
  "text": "Вот моя фотография",
  "photo_id": "photo_01"
}
```

Сервер проверяет владельца, помечает фото опубликованным и рассылает сообщение с метаданными снимка. После этого изображение доступно всем авторизованным игрокам. Текст можно не передавать, если есть `photo_id`.

**9. Какие файлы зафиксировать в репозитории**

В вашей структуре предлагаю:

```text
docs/
  api/
    conventions.md
    openapi.yaml
    websocket.md
    examples/
      world.snapshot.json
      room.json
      players.state.json
      guide.completed.json
```

- `openapi.yaml` — HTTP-маршруты, схемы, cookie-авторизация, ошибки.
- `websocket.md` — события, направления, порядок и правила переподключения.
- `conventions.md` — координаты, лимиты и правила учёта кеша.
- `examples/` — согласованные фикстуры для разработки фронтенда.

**Первым фиксируем и реализуем:** вход → `/me` → WS snapshot → manifest и зал → движение → чат → вопрос гиду. Фотографии добавляются следующим блоком. Такой порядок позволит фронтендеру уже по фикстурам строить сцену, пока бэкендер реализует сессии и сетевой цикл.
