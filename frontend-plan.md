# План фронтенда (16 часов)

Основа: **Three.js** (требование организатора: в основе Babylon.js или three.js, остальные библиотеки допустимы как дополнение), TypeScript, Vite, HTML-интерфейс поверх canvas. Сеть и бюджет памяти определяет `api.md` (API v1). Он главнее этого плана: если они расходятся, прав `api.md`.

Принципы:

1. **Залы с первого часа грузятся через загрузчик с бюджетом.** Первый зал не делается захардкоженной сценой. Иначе на 3-м часу придётся переписывать мир под лимит 10%, а это самое рискованное требование.
2. **Работа на моках, без ожидания бэкенда.** Моки повторяют контракт `api.md` один в один: те же маршруты `/api/v1`, те же события, тот же порядок (`world.snapshot` первым, `world.ready` до движения). Реальный бэкенд подключается переключателем, без правки логики.
3. **Один WebSocket `/api/v1/ws`** на всё: игроки, чат, стрим гида. Одна логика переподключения.
4. **Второй день: сначала функции, потом красота.** Визуальную часть можно ужать, если не хватит времени.
5. **Только то, что есть в v1.** Мини-карты, заданий, личных сообщений, моделей и предзагрузки соседних залов в API нет. Их не делаем.

## Что нужно от клиента по `api.md`

- **Вход:** `POST /auth/register`, `/auth/login`, `/auth/logout`, `GET /me`. Сессия в cookie `museum_session` (HttpOnly), токен руками не трогаем.
- **Подключение:** WS, первое сообщение `world.snapshot`. Дальше `GET /world/manifest`, сверка `world_version`, загрузка `current_room` (описание + assets, все запросы с `?version=`), затем `world.ready {world_version, movement_epoch}`. До подтверждения `world.ready` движение, осмотр, вопросы гиду и фото не отправляем.
- **Команды WS:** у всех, кроме `player.move`, `request_id` (UUID v4). Конверт `{type, request_id?, payload}`.
- **Движение:** `player.move {movement_epoch, seq, position, rotation}` 10 Гц, `seq` растёт в пределах epoch. Скорость ≤ 4 м/с, цилиндр r = 0,3 м, камера выше позиции на 1,65 м, Y позиции всегда 0. Клиент сам считает коллизии с `surfaces` (`collidable`) и `bounds`: сервер отклоняет весь шаг при пересечении. Свою позицию корректируем по `players.state` и `ack_seq`.
- **Углы:** `yaw` вокруг +Y, `pitch` вверх, взгляд при нуле вдоль −Z. Это совпадает с Euler `YXZ` в Three.js. Экспонат при `rotation_y = 0` смотрит в +Z, как `PlaneGeometry`.
- **Переход:** `world.enter {door_id, movement_epoch}`. Блокируем движение, ждём `world.entered`, выгружаем старый зал, грузим новый, шлём `world.ready`. Epoch после перехода новый, `seq` с 1.
- **Осмотр:** `exhibit.inspect {exhibit_id}` в радиусе 3 м, ответ `exhibit.inspected`.
- **Чат:** `chat.send {text?, photo_id?}`, текст 1–500 символов, события `chat.message`. История чата не хранится.
- **Гид:** `guide.ask {guide_id, text, exhibit_id?}` → `guide.accepted` → `guide.started` → `guide.delta {index, text}` → `guide.completed` (его `text` заменяет все delta) или `guide.failed`. `guide.cancel {generation_id}`. История: `GET /guides/{id}/generations`. Номера в очереди нет: показываем «Ожидание» и «Гид отвечает».
- **Фото:** `POST /photos` (multipart: `image`, `room_id`, `movement_epoch`, `caption?`, `exhibit_id?`) с заголовком `Idempotency-Key`. Альбом `GET /photos?limit=6&cursor=`.

### Технические решения для бюджета 10%

- Лимит берём из манифеста: `client_cache_limit_bytes = floor(total_content_bytes / 10)`. В числитель входят файлы зала, их резервы загрузки, фото и резервы фото. HUD считает сам по этим правилам.
- Загружен ровно один зал (`max_loaded_rooms: 1`). Предзагрузки соседа нет. При переходе сначала отмена загрузок и полная выгрузка старого зала, потом загрузка нового. Показываем затемнение на время перехода.
- Все ресурсы зала грузим через `fetch(url, { cache: 'no-store' })`, затем `createImageBitmap` и `THREE.Texture`. Так байты считаются точно и нет скрытого HTTP-кеша. `THREE.Cache` не включать, Service Worker не добавлять. `TextureLoader` для контента не использовать.
- Перед загрузкой резервируем объявленные `bytes`, после загрузки заменяем фактическим размером. Если пришло больше объявленного: прервать, удалить результат, показать ошибку контента.
- Устаревшие ответы (после перехода или смены версии) отбрасываем. Для этого каждая загрузка привязана к `AbortController` и к epoch.
- При выгрузке: `texture.dispose()`, `bitmap.close()`, `geometry.dispose()`, `material.dispose()`.
- Общие ресурсы почти ничего не весят: материалы процедурные, шрифт системный, игроки и гиды из примитивов.
- Фото занимают не больше 3 МиБ: один оригинал ≤ 2 МиБ и до шести миниатюр ≤ 128 КиБ. Предыдущий оригинал освобождаем до новой съёмки. Миниатюры альбома грузим постранично (6 штук) и освобождаем при закрытии. Фото из чата: метаданные сразу, изображение только по клику и через тот же резерв.
- Для жюри: в HUD показывать `renderer.info.memory` (число текстур и геометрий). Так видно, что выгрузка действительно работает.

### Подводные камни

- `Esc` снимает pointer lock принудительно, перехватить это нельзя. Нужен экран «Кликните, чтобы продолжить». Повторный `requestPointerLock` сразу после выхода в Chrome падает с ошибкой. Ловить её и ждать клика.
- Пока фокус в `input` чата или диалога, обработчики WASD, `E` и `F` игнорируются.
- Фото: `renderer.render()` и затем `canvas.toBlob()` в одном и том же кадре. Размер кадра 1–1920 × 1–1080 (при большем окне масштабировать), формат JPEG/WebP, результат ≤ 2 МиБ: если больше, снижать `quality`. HTML-интерфейс в снимок не попадает сам. `preserveDrawingBuffer` не нужен. На время съёмки и загрузки блокируем движение и переходы.
- Повтор `POST /photos` после потери ответа идёт с тем же `Idempotency-Key`, новый снимок получает новый ключ.
- Dev-прокси Vite не меняет заголовок `Origin`: бэкенд должен разрешать `http://127.0.0.1:5173`. Cookie `Secure` на локальном HTTP отключается только настройкой бэкенда.
- Если TypeScript 7 начнёт мешать сборке или редактору, сразу откатиться на 5.x. Не тратить на это время.

## Что резать при отставании (по порядку)

1. Декор и таблички.
2. Облик гидов: портрет в рамке вместо фигуры.
