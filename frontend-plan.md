# План фронтенда (16 часов)

Основа та же, что в plan.md: Three.js, TypeScript, Vite, HTML-интерфейс поверх canvas. Отличия от общего плана:

1. **Залы с первого часа грузятся через загрузчик с бюджетом.** Первый зал не делается захардкоженной сценой. Иначе на 3-м часу придётся переписывать мир под лимит 10%, а это самое рискованное требование.
2. **Работа на моках, без ожидания бэкенда.** Типы контракта и фейковые данные готовы к 0:45. Реальный бэкенд подключается в оговорённых точках.
3. **Стрим ответа гида идёт через уже открытый WebSocket**, без отдельного SSE. Получается один канал и одна логика переподключения.
4. **Второй день: сначала функции, потом красота.** Визуальную часть можно ужать, если не хватит времени. Альбом и цель недоделанными на показ не выйдут.

## Что согласовать с бэкендером за первые 45 минут

Минимальный контракт (`src/network/contract.ts`, копия из `contracts/`):

**HTTP**
- `POST /api/login` выставляет cookie. `POST /api/logout`.
- `GET /api/me` возвращает `{ user, state: { roomId, pos, rotY } }` для восстановления.
- `GET /api/world/manifest` возвращает `{ totalBytes, sharedBytes, rooms: [{ id, wing, neighbors, doors, bytes }] }`.
- `GET /api/rooms/:id` возвращает пакет зала: параметры планировки, экспонаты (`id, title, imageUrl, bytes, text`) и гида.
- `POST /api/photos` (multipart) возвращает `{ id, url, thumbUrl }`. `GET /api/photos?page=`.

**WebSocket `/ws`**
- Клиент отправляет: `move {pos, rotY, roomId}` (10–15 Гц), `chat.send {text, photoId?}`, `guide.ask {reqId, guideId, text}`, `exhibit.view {exhibitId}`.
- Сервер отправляет: `welcome {you, players}`, `player.join` и `player.leave`, `players.snapshot`, `chat.msg`, `guide.queued {reqId, position}`, `guide.delta {reqId, text}`, `guide.done {reqId}`, `rooms.allowed {ids}`, `error`.

Ещё один вопрос до начала работы: **кто собирает картинки и тексты для 24 залов.** В плане эта задача не закреплена ни за кем, а это несколько часов работы. Лучше подготовить заранее изображения из общественного достояния, 1024 px, webp/jpg до 300 КБ.

### Технические решения для бюджета 10%

- Все ресурсы зала загружаются через `fetch(url, { cache: 'no-store' })`, затем `createImageBitmap` и `THREE.Texture`. Так байты считаются точно и нет скрытого HTTP-кеша. `THREE.Cache` не включать. `TextureLoader` для контента не использовать.
- При выгрузке: `texture.dispose()`, `bitmap.close()`, `geometry.dispose()`, `material.dispose()`.
- Общие ресурсы почти ничего не весят: материалы процедурные, шрифт системный, NPC собраны из примитивов. Тогда `sharedBytes` едва влияет на процент.
- Миниатюры альбома тоже учитываются в бюджете. Загружать постранично (не больше 6 по 320 px) и освобождать при закрытии.
- Для жюри: в HUD показывать `renderer.info.memory` (число текстур и геометрий). Так видно, что выгрузка действительно работает.

### Подводные камни

- `Esc` снимает pointer lock принудительно, перехватить это нельзя. Нужен экран «Кликните, чтобы продолжить». Повторный `requestPointerLock` сразу после выхода в Chrome падает с ошибкой. Ловить её и ждать клика.
- Пока фокус в `input` чата или диалога, обработчики WASD, `E` и `F` игнорируются.
- Фото: `renderer.render()` и затем `canvas.toBlob()` в одном и том же кадре. HTML-интерфейс в снимок не попадает сам. `preserveDrawingBuffer` не нужен.
- Если TypeScript 7 начнёт мешать сборке или редактору, сразу откатиться на 5.x. Не тратить на это время.

## Что резать при отставании (по порядку)

1. Мини-карта и декор.
2. Облик гидов: портрет в рамке вместо фигуры.
3. Подписи к фото в чате: только картинка.
4. Предзагрузка соседа: оставить один зал и затемнение при переходе.
5. Онбординг: оставить только подсказки управления.

**Не резать ни в коем случае:** вход, мультиплеер, загрузку с бюджетом и HUD с процентом, диалог с гидом, фото.
