**Для вашей идеи рекомендую: Three.js + TypeScript + Vite на фронтенде, Go + PostgreSQL на бэкенде, Ollama с локальной моделью Qwen на серверном ноутбуке.** Два отдельных репозитория, один адрес для игроков в локальной сети.

За **16 часов на каждого разработчика** получится сделать галерею с перемещением, другими игроками, фотографиями и гидами с памятью. Для этого нужны простая архитектура залов, готовые изображения и небольшие текстовые базы знаний.

**Что именно делаем**

Игрок входит в галерею, исследует тематические комнаты, фотографирует экспонаты, общается с другими посетителями и задаёт свободные вопросы историческим персонажам.

Для демонстрационного маршрута достаточно трёх тем:

| Тема | Гид | О чём можно поговорить |
|---|---|---|
| Древний Египет | Геродот | Путешествия, культура, памятники |
| Возрождение | Леонардо да Винчи | Перспектива, живопись, наблюдение |
| Искусство и пространство | Эйнштейн | Пространство, свет, связь искусства и науки |

Гиды обозначаются как художественные реконструкции. Они опираются на подготовленные материалы и признают, когда вопрос выходит за пределы их знаний.

**Социальная механика:** чат и возможность отправить другому игроку фотографию с подписью. Небольшая цель — собрать фотоальбом из трёх экспонатов разных эпох и обсудить их с гидами. Это даёт образовательный смысл без разработки сложной системы квестов.

Управление: WASD, мышь, `E` — взаимодействие, `F` — фото, `Esc` — освободить курсор. Предполагается игра на ноутбуках; поддержка шлемов в этот объём не включена.

**Выбор стека**

Под «официальными библиотеками» здесь понимаю оригинальные пакеты от их сопровождающих, без форков и самописных замен. Важно: `pgx` и `coder/websocket` — сторонние проекты, а не библиотеки команды Go. В стандартной библиотеке Go нет полноценного PostgreSQL-драйвера и серверной реализации WebSocket; писать их самостоятельно за два дня неразумно.

**PostgreSQL или SQLite**

Для одной локальной игры SQLite была бы проще: один файл, минимум настройки. Но **в вашем случае оставил бы PostgreSQL**, если бэкендер уже умеет с ней работать:

- удобно хранить сессии, сообщения, фотографии и память NPC;
- понятная работа с одновременными запросами;
- не понадобится менять хранилище после хакатона.

Дополнительная сложность — установка и запуск отдельного процесса. Docker Compose подходит, если Docker уже настроен; на его установку и диагностику не стоит тратить первый день. Версию PostgreSQL выбрать из [актуальных стабильных выпусков](https://www.postgresql.org/docs/release/) и закрепить точный тег.

Минимальные таблицы: `users`, `sessions`, `player_states`, `dialog_messages`, `guide_memories`, `photos`. Контент галереи хранить файлами.

**Локальная модель для RTX 4070 Laptop**

Стартовый кандидат — **Qwen3.5 4B через Ollama**. Официальный каталог предлагает `qwen3.5:4b`, пакет около 4 ГБ. Это размер модели на диске, а не полное потребление VRAM. [Карточка модели](https://ollama.com/library/qwen3.5:4b).

В первый час проверить реальный объём свободной VRAM и скорость на вашем ноутбуке. Начальные настройки:

- контекст около 4096 токенов;
- короткие ответы, примерно 150–250 токенов;
- одна активная генерация, остальные запросы в очереди;
- отключённое рассуждение, если выбранная модель поддерживает этот режим;
- потоковый вывод текста;
- запасной вариант — меньшая модель того же семейства при нехватке памяти.

Ollama запускается на ноутбуке с RTX; Go обращается к нему через локальный HTTP API. Браузеры общаются только с Go. Поддержку параметров конкретной модели нужно проверить через `/api/show`; потоковая генерация предусмотрена в [официальном API](https://docs.ollama.com/api/chat).

**Одна модель обслуживает всех гидов.** Для каждого запроса Go собирает:

1. Личность и правила поведения гида.
2. Материалы текущей комнаты.
3. Найденные фрагменты по вопросу.
4. Последние сообщения.
5. Память: что игрок видел, фотографировал и обсуждал.

Первый день — последние сообщения и структурированные события. Второй — краткое резюме длинных диалогов. Память хранить по паре `user_id + guide_id`.

Для маленького корпуса достаточно поиска по словам и тегам. Векторная БД, отдельная embedding-модель и агентный фреймворк здесь не окупятся.

**Сессии, сеть и два репозитория**

Репозитории:

```text
gallery-frontend
  src/scene/
  src/network/
  src/world/
  src/ui/
  src/photo/

gallery-backend
  cmd/server/
  internal/auth/
  internal/world/
  internal/realtime/
  internal/guides/
  internal/storage/
  migrations/
  content/
  contracts/
```

Бэкендер ведёт `contracts/`: HTTP API, форматы WS-событий и примеры JSON. Фронтендер получает зафиксированную копию контракта. Для 16 часов этого достаточно; автоматическую генерацию SDK можно отложить.

Раздельные репозитории **не требуют разных адресов в браузере**. На демонстрации Go раздаёт собранный фронтенд и API с одного origin. В разработке Vite проксирует `/api` и `/ws` в Go.

Авторизация:

- вход создаёт случайный session token;
- в БД хранится его хеш, пользователь и срок действия;
- браузер получает `HttpOnly`, `SameSite` cookie;
- сервер проверяет сессию и `Origin` до открытия WebSocket;
- выход отзывает сессию и закрывает связанные соединения.

Для HTTPS cookie получает `Secure`; для изолированного HTTP LAN-запуска нужна явная конфигурация без этого флага. Аккаунты для первого показа можно создать заранее, оставив пользователю обычный вход.

Движение: 10–15 сообщений в секунду, интерполяция на клиенте, проверка скорости и границ на сервере. Позиция сохраняется периодически; диалоги и фотографии — при изменении.

**Подгрузка мира и лимит 10%**

Это наиболее рискованное требование. **Три комнаты, полностью загруженные на клиент, его не выполняют.**

Предлагаю мир из **24 небольших залов**, собранных из общего шаблона. Они объединены в три тематических крыла; каждый зал имеет экспонаты и экземпляр подходящего гида. Подробно оформляем демонстрационный маршрут, остальные наполняем пакетно из подготовленной коллекции — без пустых залов для искусственного увеличения знаменателя.

Клиент держит текущий зал и максимум один соседний. Два из 24 — 8,33% по количеству, но обязательная проверка идёт **по объёму данных**:

```text
загруженные данные + зарезервированные загрузки
    ≤ 10% общего объёма контента мира
```

- Сервер сообщает размеры пакетов и разрешённые рядом с игроком залы.
- Перед загрузкой клиент резервирует бюджет.
- Старые пакеты удаляются до получения новых.
- Текстуры, геометрия и материалы освобождаются через `dispose()`.
- Для контента отключается постоянный HTTP-кеш; Service Worker не используется.
- Каждый зал заранее проверяется на возможность загрузки в пределах бюджета.
- Если два зала не помещаются, остаётся один и короткий переход с загрузкой.

Общие ресурсы также учитывать; отдельно измерять фактическую RAM/GPU-память после декодирования. Определение «общих данных мира» согласовать с организаторами в начале работы.

Фотографии хранить на сервере. На клиенте ограничить текущий снимок и страницы альбома, чтобы альбом не превращался в бесконечный второй кеш. Консервативно включить их клиентские копии в бюджет до уточнения правил.

**Как реализовать фото**

Первый день: кнопка делает кадр Three.js-сцены без интерфейса и позволяет скачать изображение. Рендерить кадр непосредственно перед захватом canvas; не включать постоянно `preserveDrawingBuffer` только ради редких снимков.

Второй день: отправка снимка на сервер, альбом и публикация ссылки в чат. Все текстуры загружаются с вашего сервера, чтобы захват canvas не блокировался из-за сторонних ресурсов.

**Правила, которые удержат проект в сроках**

- На третьем часу уже должен работать мультиплеер; интеграция начинается в первый день.
- Модель скачивается и проверяется в самом начале, а не после написания чата.
- Архитектура залов строится из примитивов; NPC — простая фигура или портрет с именем.
- Все изображения, шрифты, зависимости и модель заранее доступны локально.
- В последний час каждого дня добавление функций прекращается.
- При отставании сокращаются декор, количество уникальных личностей и функции альбома. Авторизация, подгрузка, лимит кеша, локальный ИИ с памятью и сохранение остаются обязательными.

**Критерий готовности:** два человека без интернета могут войти, встретиться в галерее, поговорить, сделать фото и получить персонализированный ответ гида; сервер восстанавливает состояние, а клиент на протяжении всего маршрута соблюдает лимит 10%.
